## Review findings for implementation

1. The iPhone `ForwardToWatch` and `ConfirmWatchErase` use cases are implemented, but the iPhone composition has no `WatchLink`, receipt stream, or Watch request driver yet. The completion path must read and send the newest permitted committed payload after a matching receipt, while a pending clear blocks newer usage in every channel and reply. Test widget-origin and interrupted app commits caught up on app launch as well as ordinary app commits. A current `CommitEvent` must not be used after a newer commit or Forget Mac changes the reader bundle.
2. The Watch uses transactional `WatchCacheStore` for its snapshot, installation ID, revision, tombstone, and erase hold. Review the existing `try?` failure paths in `CommitWatchPayload`, `ForwardToWatch`, and `ConfirmWatchErase`: distinguish storage failure from ignored or confirmed receipts; failed context sends and receipt queues must remain observable and retryable. A clear receipt follows durable empty-cache commit and a complication reload request. `SurfaceReloader` currently returns no result, so a submitted reload request cannot prove the rendered frame was erased. A same-revision conflicting payload must never be accepted as an idempotent replay.
3. A changed iPhone installation requires owner confirmation of the exact held payload. Reset Watch Pairing after local erase may release a hold but must retain the revision floor for the same installation. An old clear, stale usage message, duplicate receipt, or late relay result must not restore forgotten data.
4. WatchConnectivity has two inbound payload channels with different delivery timing. Route both through one codec and `CommitWatchPayload`; test channel reordering, malformed or unknown versions, bounded property-list input, session activation and reachability changes, background-task completion, reply completion, and duplicate queued receipts. Confirm the payload omits transient manual-request results and all secrets.
5. The complication transfer budget is an iPhone policy backed by persisted reader state. Check the rolling 24-hour cap, 30-minute spacing, enabled flag, paired/install/activation state, remaining system transfers, and Home-slot change filter before sending; application context remains the authoritative latest-value channel. Make the persisted budget reservation and failed-transfer behavior explicit, so retries cannot overspend or silently suppress an eligible later change. The complication timeline must age cached observations from their original times even if watchOS delays a reload.
6. Watch installation and App Group behavior under free Personal Team signing are physical-device questions. A simulator pass cannot establish paired Watch installation, background delivery, or complication reload. Apple also says the simulator does not support `transferCurrentComplicationUserInfo`. Record package contents, installed entitlements, OS/build versions, elapsed times, and observed outcomes without identifiers, pairing packages, credentials, or raw provider data. Keep seven-day refresh preservation as a separate Phase 1 exit observation. [Apple's transfer documentation](https://developer.apple.com/documentation/watchconnectivity/wcsession/transfercurrentcomplicationuserinfo%28_%3A%29)
7. The archived [P1-M2 open-work record](../archive/p1-m2-open-work.md) assigns paired WatchConnectivity and runtime security proof to the owning modules. Use it as a record, not as an active plan. A security table is complete only when each implemented trust boundary has evidence or an explicitly recorded accepted residual; M9's waived exit is not a pass for its remote checks. M16 can finish with the table assembled and its Watch rows closed while other named rows remain open for Phase 1.
8. `WatchLink` currently exposes only sends, while the design also needs active-session, installed-app, enabled-complication, and remaining-transfer state. Specify that port boundary during implementation and test a disabled complication or exhausted system budget without suppressing the authoritative application context. Apple's [WCSession documentation](https://developer.apple.com/documentation/watchconnectivity/wcsession) requires activation before transfers and checks pairing and installation before iPhone sends.
9. The current payload model represents a committed iPhone revision; a Watch refresh with no permitted payload needs an explicit, bounded empty reply rather than a fabricated cleared payload or revision. Define the reply shape and one-shot completion at the adapter boundary. Reject malformed request and receipt messages before they reach a use case, and test an ingest that finishes after the reply deadline.
