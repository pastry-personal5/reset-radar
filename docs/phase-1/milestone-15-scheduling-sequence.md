# P1-M15: Scheduling sequence

Status: Planned

Implementation and verification order for the [M15 overview](milestone-15-scheduling-overview.md). The existing [Scheduling](../architecture/scheduling.md), [iOS app](../architecture/ios-app.md), [Application](../architecture/application.md), [Storage](../architecture/storage.md), and [approved UX](../ux-gui.md) remain the behavior contracts.

## 1. Establish the M14 handoff and baseline

Bring the completed M14 reader app, plan, and restored iPhone/iPad gate into this branch. Record the exact revision, clean worktree state, reference iOS 26.1 destinations, and complete baseline gate. Inspect actual app and widget object graphs, app/widget Keychain and App Group entitlements, `ReaderStore` transaction boundaries, and post-commit hooks. Resolve the M14 owner questions where they affect M15. M9 remains a separate active gate; its exit does not block this work, and M15 tests must not claim the M9 cellular or billing results.

Write a synthetic-data device runbook before using a paired owner device. Record commands, OS and build versions, expected vs observed results, and elapsed times without tokens, pairing packages, raw provider payloads, or account identifiers. Start the 24-hour background interval observation as soon as the installable task driver exists.

## 2. Validate ActivityKit behavior and contract gaps

Run the owner-required iPhone ActivityKit spike with a synthetic eligible five-hour window: foreground start, content update, stale rendering, reset or invalidation end, system expiration near eight hours, app suspension, and no Activity on iPad. Capture device behavior and any mismatch with the approved lifecycle before freezing adapter or view behavior. Do not turn a system limit or delayed callback into a guessed reset rule.

Review the Application gaps in the overview before wiring UI: provisional authorization, durable `needsAppReconcile` completion after retryable notification work, Reset Radar-only notification ownership, and missing alias/product/activity display fields in the port payloads. Keep policy and snapshot-derived display data in Application and framework mapping in Scheduling. Implement the owner's all-window choice with a standard `AccountWindow` or additional concrete `WindowID` selection, preserving existing standard opt-ins. Add focused regressions where the existing contract must be corrected.

## 3. Implement Scheduling and Mac reset notifications

Implement `NotificationScheduler` with `UNUserNotificationCenter`: map authorization states including quiet provisional authorization, build namespaced identifiers and alias/product/window copy from Application-provided data, and schedule non-repeating UTC calendar triggers for absolute reset instants. Reconcile only Reset Radar-owned requests for all valid provider windows. Compare complete pending content as well as the fire instant, so alias or window-label edits replace stale copy. Use `SetNotificationOptIn` from each Account Details window action; leave denied choices recorded and show the Settings route rather than repeatedly prompting. Reconcile after commits, owner choice, permission changes, alias/window-label changes, time-zone/clock changes, account replacement, and startup. Verify the same reset can alert on multiple devices because each has independent preferences. Exercise the largest valid window set the source can supply and record any platform pending-request limit rather than promising delivery from a successful scheduling call alone.

Wire the M12 `ResetNotificationHook` in the Mac environment. Mac General Settings shows authorization state; Account Details owns the per-window control. Exercise background Mac collection with its main window closed, changed reset, removed account, denied permission, and later permission change. Confirm notification work cannot interrupt collection or publication.

Implement `LiveActivityController` behind iOS-only ActivityKit compilation. Map the `ResetActivityAttributes` content and `staleDate` from `ReconcileLiveActivities`, keeping only immutable window identity in static attributes and the displayed alias in dynamic content so a rename updates a running activity. List only this app's activities and end with immediate dismissal. Keep the iPad controller unavailable and never start an activity from a background, widget, or refresh driver.

## 4. Complete app and widget scheduling pipelines

In the app process, run widget reload, reset-notification reconciliation, and Live Activity reconciliation after a committed ingest; on launch and foreground activation, repeat durable work left by a widget commit or app-side stage failure. Keep the pending marker when any required stage fails, its state write fails, or a newer snapshot arrives. On Forget Mac, cancel only the old publisher's Reset Radar requests and activities, confirm no owned pending request remains, reload widgets, and retry unfinished local cleanup before pairing again. A late fetch must not repopulate any surface.

Register the single `BGAppRefreshTask` exactly once before app launch completes, with its checked-in identifier; a failed registration is a visible diagnostic, not a silent loss of refresh. Submit one replaceable request when leaving the foreground and after each task, using `ReaderRefreshPolicy.nextBackgroundRequest`; the system may delay or skip it. Record submission failure and retry on the next eligible app event. The expiration handler cancels ingest, the completion handler always runs once, and the success value reflects the actual outcome. Do not post a manual Codex request. Add fake scheduler/clock tests for launch, duplicate registration/submission, reset-proximate dates, first-run state, expiration, offline or locked Keychain, failed submission, and resubmission. [Apple's background-task guide](https://developer.apple.com/documentation/uikit/using-background-tasks-to-update-your-app) requires registration during launch and treats `earliestBeginDate` as scheduling input, not an execution promise.

Give the widget extension its own injected object graph over the shared bundle and Keychain access group. On a WidgetKit timeline request, call `IngestRelaySnapshot(.widgetReload)` with the bounded client timeout; policy enforces the five-minute successful-refresh threshold and the shared 15-second minimum. Never use a preflight or uncommitted response. After a widget commit, reconcile already-opted-in notifications within the remaining extension time and persist app catch-up work. Verify cross-process claim contention and expiration with independent store instances, plus interruption before and after the committed write.

## 5. Build widget, App Intent, and Live Activity views

Replace the placeholder widget bundle with `systemSmall` Home Screen and `accessoryRectangular` Lock Screen widgets configured for any valid account window, and a `systemMedium` Home Screen widget configured for one account's standard windows. Build selection from stable account and window identity in the committed cache, using `LoadUsageDetails` or an equivalent Application query for additional valid windows that `LoadHome` does not expose. A removed selection becomes unavailable rather than retargeting another window and resumes only when the exact ID returns. Render alias with the approved truncation, percentage used, reset and freshness state, and no invented zero. Emit an entry now and at each known reset or invalidation boundary, while avoiding unnecessary dense entries elsewhere; use dynamic date text for the countdown. Request the next reload at the earlier approved change instant or fifteen minutes, while treating that date as an earliest request that the system may delay. Verify stale and post-reset display when a reload is late or the extension never runs. [Apple's WidgetKit guidance](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date/) recommends roughly five-minute spacing between entries and describes a system reload budget.

Use a `WidgetConfigurationIntent` with a dynamic, cache-only window picker and an `AppIntentTimelineProvider` for the configurable widgets. Keep this configuration intent distinct from the read-only usage App Intent: the latter accepts the same exact all-window selection and returns only committed-cache percentage, reset time, source, observation time, and state. Neither intent's parameter query fetches from the relay, and the read-only intent's action never fetches. Keep result and widget configuration behavior consistent for missing, stale, expired, and incompatible windows. [Apple's configurable-widget guide](https://developer.apple.com/documentation/widgetkit/making-a-configurable-widget/) documents the intent/provider pairing.

Add the foreground Start Live Activity action to eligible iPhone Account Details. The Lock Screen and Dynamic Island views use the shared attributes, system timer text ending at zero, and `isStale` after the observation's current-data expiry. A stale reading stays visible until its known reset unless the observation becomes invalid for another reason. Reconcile on app commits and next app execution after widget commits; end when the reset passes, the observation or account is invalid, the owner forgets the Mac, or the system disables activities. An app that never runs at reset cannot guarantee immediate dismissal; the system's eight-hour activity limit is the final fallback. Show availability in Settings and keep the action absent on iPad and weekly windows. [Apple's ActivityKit lifecycle guidance](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities) describes stale presentation and the system limit.

Run focused Scheduling, Application, app, widget, App Intent, and UI tests while implementing. On iPhone, verify Live Activity start, update, stale appearance, reset end on the next app execution, and iPad absence. On Mac, verify local notification delivery from the collector without its main window. Record the actual 24-hour background-task intervals, including gaps; do not infer guaranteed background delivery from an earliest begin date.

Run the complete [contribution-guide gate](../contribution-guide.md#required-validation) from the final worktree, with M14's iPhone and iPad tests enabled. Inspect generated target entitlements and `git diff --check`; check local Markdown links. Update affected user-facing, installation, architecture, phase, and changelog docs with the implementation evidence. Leave unchecked any criterion without direct evidence, especially physical-device or elapsed-time checks.
