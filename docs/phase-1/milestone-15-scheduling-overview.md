## In scope

- Implement the `ResetRadarScheduling` adapters for local reset notification requests on iPhone, iPad, and Mac, and ActivityKit operations on iPhone. Wire the M12 Mac post-commit notification hook, per-window controls in Account Details, and authorization status in Settings. Keep opt-in off by default and device-local; request permission only from a user action.
- Reconcile one pending request per opted-in valid provider-reported window against the latest committed snapshot, including additional Account Details windows. Keep standard Home selections stable across provider-scope changes, and tie additional selections to their concrete `WindowID` so a new scope or limit cannot inherit an old opt-in. Replace or cancel a request when its reset or copy changes, the window disappears or expires, the account or source becomes ineligible, authorization changes, or the owner changes the opt-in. Keep the fire instant absolute through time-zone changes. The widget extension may reconcile already-authorized requests after its own commit, never prompt.
- Wire one `BGAppRefreshTask` identifier, policy-computed earliest begin date, resubmission, cancellation on expiration, and an honest completion result. Continue foreground and manual paths from M14. No background timing promise or push path is added.
- Replace the widget scaffold with configurable `systemSmall` Home Screen and `accessoryRectangular` Lock Screen widgets for any valid window, plus a `systemMedium` Home Screen widget for one account's two standard windows. Use an exact saved selection, the committed cache, policy-limited relay ingest on a WidgetKit reload, timeline entries at presentation changes, and an unavailable state when a selected window disappears. Add the read-only all-window App Intent with no network call. Treat reload dates as requests, never delivery guarantees.
- Add iPhone-only foreground Start Live Activity for an eligible five-hour standard window, local updates and end conditions, and Lock Screen/Dynamic Island views with a system countdown and stale presentation through the known reset. ActivityKit availability and the iPad absence are explicit. Perform the required ActivityKit device spike before freezing the implementation.
- Complete the app/widget reconciliation handoff and Forget Mac cleanup. An interrupted widget notification pass remains retryable; the app catches up Live Activities and other pending work on its next execution. Widget and activity surfaces never show preflight, invalid, or post-forget data.
- Verify tests and owner-run physical-device behavior, including app/extension App Group and Keychain access, notification delivery and time-zone behavior, WidgetKit reload limits, Live Activity lifecycle, background-task intervals over 24 hours, and Sideloadly re-sign preservation of extension access.

## Review findings to resolve during implementation

1. The committed `NotificationAuthorization` model has only `notDetermined`, `denied`, and `authorized`, while [Scheduling](../architecture/scheduling.md#reset-notifications) describes `provisional`. Map the system's provisional grant as quiet authorization with honest Settings copy, not as full authorization or denial. Cover any unexpected authorization state without trapping or inventing a grant.
2. `AfterCommitPipeline.run` currently clears `needsAppReconcile` after calling stages with no outcome, even when notification reconciliation reports `retryable`; its state write also suppresses errors. App-side scheduling failure has no durable retry marker either. Preserve pending work until all required stages succeed for the still-current snapshot, and prove interrupted or contended widget and app reconciliation resumes without losing a newer commit.
3. Notification cancellation must be limited to Reset Radar's own request identifiers, including Forget Mac cleanup. The existing `ResetRequest.identifier` and `PreferenceStore` keys represent only standard `AccountWindow`s; preserve standard request IDs and opt-ins during migration, define a bounded deterministic identifier for concrete additional windows, and reject malformed or foreign pending requests. Apple documents pending-request removal as asynchronous, so Forget Mac must confirm owned requests are gone or keep local cleanup pending. Test removal, scope replacement, duplicate legacy requests, and unrelated requests. [Apple notification removal API](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/removependingnotificationrequests%28withidentifiers%3A%29)
4. The port payloads do not carry all approved display data: `ResetRequest` has no alias or product for notification copy, and `LiveActivityController.start` receives no alias or source state/precision for activity content. Derive these from the committed snapshot in Application and pass typed, bounded display values to Scheduling; the adapter must not read Storage or invent copy. `ReconcileResetNotifications` currently compares only `fireAt`, so alias or provider-window-label changes would leave stale pending copy; compare the complete desired request. Keep the Live Activity alias in dynamic content so a local rename updates it without an automatic restart.
5. The committed M15 branch still has the scaffold app and widget, while M14's active checkout has unfinished code and unresolved owner questions. Its untracked draft still names M9 `Done` as an entry requirement, contrary to the owner's M9-gate waiver and the updated phase dependency table. Reconcile that draft during the M14 handoff, then verify the actual merged implementation before wiring scheduling or claiming the iOS gate passed.
6. Committed `LoadHome` exposes standard Home slots. Use `LoadUsageDetails` or an equivalent committed-cache query to offer all valid windows to small/Lock Screen widgets and the App Intent, with exact identity and an unavailable result after removal. The [iOS widget design](../architecture/ios-app.md#widget-extension) now records this contract.
7. Apple documents WidgetKit timelines and reloads as system-budgeted, and recommends entries spaced about five minutes apart. Request a known reset or invalidation entry even when it is close, avoid unnecessary dense entries, and treat a "next reload" as an earliest request rather than a guaranteed refresh or exact threshold rendering. Use dynamic dates where possible and verify stale and reset transitions when the extension does not run. [Apple WidgetKit guidance](https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date/)
8. Register the sole `BGAppRefreshTask` before app launch completes and only once; test a failed registration or submission, cancellation, completion, and resubmission. A scheduled earliest begin date is not a cadence guarantee. [Apple background-task guidance](https://developer.apple.com/documentation/uikit/using-background-tasks-to-update-your-app)

## Selection contract

The approved [UX](../ux-gui.md#account-details) and the owner's 2026-10-26 answers require all valid windows for reset notifications, small Home Screen and rectangular Lock Screen widgets, and the read-only App Intent. Model a saved `WindowSelection` as either the stable `AccountWindow` for an account's default five-hour or weekly window, or the concrete `WindowID` for an additional window. The latter includes provider scope and limit identity, so a changed or removed window becomes unavailable rather than silently selecting a sibling. Keep the existing standard opt-in values when migrating storage. A missing additional window has no scheduled request; a subsequent report of the exact same identity resumes its retained opt-in and widget selection, while a different identity needs a new choice. Medium widgets, Home rings, Watch complication, and five-hour Live Activities continue to use standard windows.
