# Claude Code Mod usage research (Claude Code)

Status: Active

An independent check of whether a Claude Code Mod can collect Claude Code usage for Reset Radar. The check used the declarations generated by Claude Code 2.1.310 and an owner-present, signed-in probe on 2026-10-25. It adds signed-in evidence to the public-source study in [Claude Code Mod usage acquisition](phase-1/claude-code-mod-usage-acquisition.md), and adopting a Mod remains an owner decision.

## Verdict

**Yes.** A Mod receives the same provider-reported five-hour and seven-day percentage used and reset time that the [Claude Code status line](../architecture/provider-adapters.md#claude-code-status-line) receives. In two same-session comparisons, the Mod's readings equaled the status-line helper's records exactly.

**Three conditions apply:**

- **Not an independent usage query.** Like the status line, a Mod only reports what the session's last API response carried. It cannot refresh an idle session's reading, so the existing freshness and [dropped-window](../architecture/provider-adapters.md#dropped-windows) rules still apply.
- **`$.fs` alone cannot write Reset Radar's records safely.** It has no file mode or rename, and the probe's file was observed world-readable. A Mod could call `chmod` and `mv` through `$.process.run`, but once a process call is needed, Reset Radar's signed helper is the cleaner writer.
- **The API is early access.** The generated declarations say the surface "may change between releases without notice". The status line is a documented interface.

**Recommendation:** keep the status line as the production source, and do not add a Mod as a second feeder. Revisit only if one of the [open questions](#open-questions) turns up a coverage gap the status line cannot close. In that case, prefer replacing the status line over running both sources.

## Evidence

"Types" means the declarations Claude Code 2.1.310 generated. "Probe" means the [run below](#probe-record).

| Status-line input ([decoder allowlist](../architecture/provider-adapters.md#helper-composition)) | Mod | Note |
|---|---|---|

## Observation time

Like the status-line input, `SessionRateLimit` carries no observation time. The helper's [observation-time rule](../architecture/provider-adapters.md#observation-time) needs a response signal, and a Mod has two candidates:

- **A `session.measure` whose `changed` includes `cost`.** The declarations say `cost` means the total grew, which happens on a priced response. The probe's two pushes both carried it. Only the unit's name is read, never the amount. This differs from the sibling study, which excludes cost entirely.
- **A `turn.step` hook,** which runs once per model request and names subagents through `agentId`. It is more precise, but it is a streaming hook with its own time budget. Not probed.

A `session.start` reading is cached, not a new observation. In the probe, the reading at load was superseded by a push two seconds later.

The probe also showed how coarse the push is:

- One long turn with many model requests produced only two pushes, each with `rateLimits` in `changed`. Mid-turn pushes therefore follow whole-point moves, not every response.
- A `cost`-based rule would advance `observedAt` only at turn ends and on point moves. That is coarser than the helper's per-response `total_api_duration_ms` rule.
- In a long turn where no window moves a point, a Mod-fed `observedAt` would lag, and could cross the 60-minute current-data window while the data is actually current.

That gap is the main reason to test `turn.step` before choosing a rule.

## Candidate designs

These are owner decisions. [ProviderAdapters](../architecture/provider-adapters.md) is binding under [AGENTS.md](../../AGENTS.md), and "Claude Code status line" is the only approved acquisition-source term.

1. **Status line only (current).** Implemented and calibrated, and needs no change.
2. **Mod as a second feeder.** The Mod calls a new record-only helper mode, and the helper validates, hashes, and writes owner-only files atomically. The two writers would need separate files per session, because both map to the same `SessionKey`; the probe found the helper's record by hashing `$.session.id()`. The collector's newest-`observedAt` merge would then span both. This doubles the surface for identical data. Not recommended.
3. **Mod replaces the status line.** Removes the `statusLine` edit, the restore record, and the [composition safety checks](../architecture/provider-adapters.md#claude-code-status-line), and frees the status-line slot for the owner. It costs:
   - early-access API churn;
   - a plugin install and removal lifecycle;
   - a new helper input mode;
   - the `claude` CLI in the validation gate, which is a build-tool change.

   Choose this only if the open questions show the status line misses sessions the owner actually uses.

## Privacy boundary

A Reset Radar Mod would be limited to:

- **Hooks:** `session.measure`, and optionally `session.start`.
- **Calls:** `$.session.usage()`, reading `rateLimits` only, plus `$.session.id()`, `$.session.version()`, and `$.process.run` with the fixed helper path.

It would not use prompt, tool, or render hooks, `$.session.messages()`, `$.settings`, `$.http`, `$.session.authorize()`, `$.session.identity()`, `$.store`, context figures, or cost amounts. The `claude plugin validate` report would be checked against this list. Because that report analyzes source statically, code review remains the real control. As with the helper, raw input is never logged or persisted.

## Open questions

None of these were tested:

- Which hosts would a Mod cover that the status line does not? The bundled reference says a user-scope install also loads in the desktop app's local Code-tab session. Still open: whether Mods load in `claude -p` and editor hosts, whether the status line runs in any of these hosts, and whether the helper path works there. This is the only question that could change the recommendation.
- Does every API response grow `cost`, and does nothing push while the session is idle?
- When a window leaves at reset, is that pushed?
- Do subagent responses move `rateLimits`?
- Do fractional percentages match the status line?
- Does `$.process.run` reach a signed helper within the hook budget, and fail harmlessly when the helper is missing?
- How do `disableAllHooks`, organization policy, two concurrent sessions, and a CLI update affect a Mod?

## Probe record

- **Setup:** Owner-present on 2026-10-25, Claude Code 2.1.310, in an interactive terminal session. The Development `reset-radar-statusline` helper was that session's status line.
- **Method:** A throwaway three-file Mod hooked `session.start`, `session.measure`, and `turn.complete`. It wrote each window's kind, percentage, and reset, plus cost, version, and session identifier, to a private scratch file. It used the session's own responses, so it made no extra model requests. The Mod and its log were deleted afterwards.
- **Retained here:** Field shapes, window kinds, match results, and relative timing only, following the [source-calibration privacy boundary](phase-1/source-calibration-spike-runbook.md#3-privacy-boundary-and-stop-conditions). No percentage, reset instant, session identifier, or cost is recorded.
- **Results:**
  - The Mod loaded after consent.
  - One `session.start` and two `session.measure` events were recorded, each with `five_hour` and `seven_day` windows that had `resetsAt`.
  - Readings moved between all three events.
  - Both comparisons with the helper's record matched on percentage and reset.
  - The Mod's file was created `0644`.
  - `turn.complete` was not observed, because the Mod was removed before a turn ended under it.
